# Deployment

Every project generated by `altair new` ships a multi-stage `Dockerfile`, a
`.dockerignore` and a `compose.yml` for SQLite, PostgreSQL and `--api` modes.
You do not need to write Docker files by hand.

## What the generator produces

The builder stage uses Crystal **1.22.3** and links the server statically;
build dependencies stay in that stage. The runtime image contains only the
compiled server, the compiled `./bin/altair` launcher, the public assets and
configuration, and the `db/migrations` files the migration runner needs.
`.env`, `.git`, `lib/`, `spec/`, local databases and build caches are excluded
from the build context and never land in an image layer.

The runtime:

- runs as a non-root `app` user;
- declares a `HEALTHCHECK` against `/health` (the generator sets
  `config.observability = true`);
- precompiles assets during the image build (`--api` projects skip the view
  and asset stages entirely);
- exposes `/health` and `/metrics` for orchestrators and scrapers.

See the [Observability guide](/docs/observability.html) for the endpoints.

## Build, migrate and run

From the generated project directory:

```sh
docker compose build
docker compose run --rm web ./bin/altair db:migrate
docker compose up -d
curl -fsS http://localhost:3000/health
```

Migrations are never automatic at container boot. The one-off `run` command
uses the same compiled launcher as local development, so what you run in
production is what you ran locally. Apply migrations exactly once, verify,
then start the web service. Migrations are compiled into the command binary
*and* their timestamped files are copied into the image at `db/migrations`,
because the runner matches those filenames to the compiled registry — a
schema change needs both a migration and a rebuilt image.

## Rollback and zero-downtime limits

```sh
docker compose run --rm web ./bin/altair db:rollback
```

`db:rollback` reverts one migration and regenerates `db/schema.cr`. Treat it
as a maintenance operation, not an automatic failure handler: rebuild the
image afterwards so the compiled schema matches the database.

The generated Compose setup runs a **single web container**. Rolling or
zero-downtime deployments need an orchestrator and a migration plan. For safe
upgrades, ship additive migrations first (nullable columns, new tables),
deploy the new binary, then remove old columns in a later release. A
destructive change needs a two-step deploy because old binaries may still
reference removed columns.

## Volumes, backups and the SQLite caveat

- **PostgreSQL:** data lives in the `pg_data` volume at
  `/var/lib/postgresql/data`. Take `pg_dump` backups before migrations and
  rehearse restores separately.
- **SQLite:** data lives in the `sqlite_data` volume mounted at
  `/app/db/data`, while `db/migrations` stays in the image at
  `/app/db/migrations`. WAL mode writes `*.db-wal` and `*.db-shm` beside the
  database, so keep all three files in the same volume and run a **single
  writer container**.

## Secrets and environment

Generated Compose files carry no real credentials. `SECRET_KEY_BASE` is
required with `${SECRET_KEY_BASE:?...}`; PostgreSQL additionally requires
`POSTGRES_PASSWORD`. Inject both from your secret manager (generate the key
with `openssl rand -hex 64`). Other supported variables are `DATABASE_URL`,
`ALTAIR_ENV`, `PORT`, `HOST_PORT` and, for PostgreSQL, `POSTGRES_USER` and
`POSTGRES_DB`. See the [Configuration reference](/docs/configuration.html).

Never commit `.env` or place credentials in an image layer.

## API projects

`--api` projects build without view or asset stages and still expose
`/health` and `/metrics`. The build → migrate → up sequence is identical.

For offline guides on the machine, see
[Offline docs and examples](/docs/docs_and_examples.html); the CLI also
answers `altair docs deployment`.
